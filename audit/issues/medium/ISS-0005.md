# ISS-0005 — Partial LiDAR registration produces a blank route

- Severity: Medium
- Status: Open
- Confidence: Confirmed
- Category: UI / usability / presentation

- Last updated: 2026-11-05

- Assigned phase: UI Phase 4

## Problem

The route has an empty state only when no LiDAR lookup is found. Once LiDAR exists, missing or mismatched servo/rangefinder dependencies return null, leaving only the shell. The page assumes fixed child lookup names.

## Evidence

Synthetic `?missingChild#/lidar` registers LiDAR without its three expected children. AX inspection shows only shell controls and no page heading or explanatory content. See `synthetic-lidar-missing-children.png`.

Source paths are relative to repository root. Line numbers refer to source revision 127dd90e0428ea0d90dfd77e48712e639d386d15; the two pre-existing firmware edits do not affect this evidence.

## Impact and severity rationale

Medium: startup ordering, incomplete firmware composition, or different child names can look like a broken application with no recovery direction.

## Root cause

Dependency resolution uses early null returns and the route lacks a partial-registration presentation model.

## Proposed resolution

Keep the LiDAR page header mounted; display missing dependency names and a waiting/configuration state. Resolve real relationships only within existing protocol capabilities; do not rename wire identifiers to solve UI copy.

## Implementation record

None. Audit and planning only; no product code changed.

## Verification and regression evidence

Baseline evidence supports the finding, not its closure. Render no LiDAR, LiDAR only, each missing child, wrong-kind child, complete registration, and incremental arrival. The page must always identify itself and explain unavailable actions.
