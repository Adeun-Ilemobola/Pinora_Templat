# ISS-0011 — Module cards omit available human-readable lookup names

- Severity: Medium
- Status: Open
- Confidence: Confirmed
- Category: UI / usability / presentation
- First observed: 2026-11-05

- Related / blocking issues: See the canonical register and assigned phase; no implementation dependency on the historical PIN-TPL audit.
- Assigned phase: UI Phase 2

## Problem

ModuleCard accepts only type, UUID and children. Multiple modules of one family all have the same visible title and are distinguished by full UUIDs even though stores retain lookup names.

## Evidence

Synthetic module cards display type plus UUID. Source confirms look_up_id is present in stores but is not passed into ModuleCard. Current firmware documentation describes three LEDs, making repeated-family identification relevant.

Source paths are relative to repository root. Line numbers refer to source revision 127dd90e0428ea0d90dfd77e48712e639d386d15; the two pre-existing firmware edits do not affect this evidence.

## Impact and severity rationale

Medium: choosing the intended physical control depends on recognizing UUIDs, which makes a clean multi-module dashboard harder to scan and use.

## Root cause

The shared card header contract omits display identity and does not expose consistent semantic headings.

## Proposed resolution

Show a human-readable name with type/status as secondary metadata; keep exact UUID available in details/copy affordance. Use real headings and accessible label references.

## Implementation record

None. Audit and planning only; no product code changed.

## Verification and regression evidence

Baseline evidence supports the finding, not its closure. Render at least three LEDs with distinct and long names plus a missing-name fallback. Check visual identification, unique control names, copied UUID accuracy, heading order and narrow wrapping.
