# ISS-0012 — LED slider label is attached to its wrapper rather than its input

- Severity: Medium
- Status: Open
- Confidence: Confirmed
- Category: UI / usability / presentation
- First observed: 2026-11-05
- Last updated: 2026-11-05
- Location: UI/src/lib/Modules/Led/view.tsx:62-75; UI/src/components/ui/slider.tsx:18-45
- Related requirements: REQ-0004, REQ-0009
- Related / blocking issues: See the canonical register and assigned phase; no implementation dependency on the historical PIN-TPL audit.
- Assigned phase: UI Phase 1

## Problem

The LED passes aria-label to Slider.Root. The Base UI generated range input has neither aria-label nor aria-labelledby, and the AX slider is unnamed.

## Evidence

Synthetic DOM inspection found an input[type=range] with aria-valuenow but no accessible name. AX shows a named container followed by an unnamed slider. The Radix PivotSlider thumb has aria-labelledby and is named correctly; this finding is specific to the shared Base UI slider path.

Source paths are relative to repository root. Line numbers refer to source revision 127dd90e0428ea0d90dfd77e48712e639d386d15; the two pre-existing firmware edits do not affect this evidence.

## Impact and severity rationale

Medium: assistive technology users cannot identify which LED control the focusable range represents, especially with several LEDs.

## Root cause

The wrapper forwards arbitrary props to Root while the focusable Thumb/input needs its own accessible label.

## Proposed resolution

Expose an explicit input/thumb naming API or use the supported Base UI field/label association; make names include the human-readable module identity.

## Implementation record

None. Audit and planning only; no product code changed.

## Verification and regression evidence

Baseline evidence supports the finding, not its closure. Inspect computed accessible names for multiple LED sliders and exercise Arrow/Home/End keys. Each focusable slider must retain name, value, bounds and disabled state.
