## Problem

LED and servo stores discard the promise returned by IncomingCommand, and their views have no pending/error result. Newer rangefinder, RFID, stepper, and LiDAR views already catch command failures and display feedback. Servo movement is also sent on every slider change while LED sends on commit.

## Evidence

Read the complete LED/servo store and view implementations and compare rangefinder/view.tsx:37-53. IncomingCommand logs and rethrows. No rejection was deliberately injected into the old controls in this audit.

Source paths are relative to repository root. Line numbers refer to source revision 127dd90e0428ea0d90dfd77e48712e639d386d15; the two pre-existing firmware edits do not affect this evidence.

## Impact and severity rationale

Medium: failed actions can appear unresponsive and users may retry without knowing what happened. Changing the servo send cadence requires an explicit interaction decision; continuous control is not itself classified as a defect.

## Root cause

Older action signatures return void and omit shared command presentation state.

## Proposed resolution

Return action promises and introduce a small reusable pending/result/error pattern. Keep reported telemetry distinct from target drafts. Define slider preview/commit behavior per actuator before changing cadence.

## Implementation record

None. Audit and planning only; no product code changed.

## Verification and regression evidence

Baseline evidence supports the finding, not its closure. Inject a controlled IPC rejection and delayed success; assert visible result, no unhandled rejection, duplicate-action handling, and no optimistic claim that hardware moved.
