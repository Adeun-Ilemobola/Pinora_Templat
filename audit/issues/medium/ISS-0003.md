## Problem

The security card can say Read-only while module command controls remain enabled, because views gate on connection and parent ownership rather than authentication capability.

## Evidence

Synthetic `?readonly` fixture sets Connected + Bluetooth + DeviceAuth NoKey. DOM inspection found Toggle LED, Start ranging, and Read mode enabled. The security text simultaneously says the desktop must pair to send commands. See `synthetic-readonly-controls.png` and `browser-observations.json`.

Source paths are relative to repository root. Line numbers refer to source revision 127dd90e0428ea0d90dfd77e48712e639d386d15; the two pre-existing firmware edits do not affect this evidence.

## Impact and severity rationale

Medium UI capability mismatch: users are invited to attempt actions the connection cannot perform. This does not establish an authentication bypass; backend authorization remains authoritative.

## Root cause

Authentication description and command eligibility have separate presentation logic.

## Proposed resolution

Introduce one typed UI capability selector (including Serial behavior, auth pending/failure/read-only, parent ownership, and busy state) and an explanatory disabled reason. Preserve backend enforcement.

## Implementation record

None. Audit and planning only; no product code changed.

## Verification and regression evidence

Baseline evidence supports the finding, not its closure. Render authenticated, USB, pending, NoKey, rejected, failed, disconnected, and parent-controlled cases. Assert write controls and handler guards match intended capabilities without real hardware calls.
