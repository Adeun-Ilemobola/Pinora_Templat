# Pinora desktop — v0.8.0-alpha

The authoritative developer entry point is the [root README](../README.md), including the alpha architecture warning, React/Zustand/Tauri boundaries, transport behavior, build commands, and limitations. The maintainer reports Bluetooth works; a complete automated hardware validation is not claimed.

From this directory, `bun run tauri dev` starts native development and `bun run tauri build` packages the desktop. `bun run build` checks TypeScript and builds frontend assets. Rust/Tauri builds work without a local Wi-Fi config: the placeholders of the [Wi-Fi config example](../protocol/src/wifi_config.example.rs) are used when the ignored `protocol/src/wifi_config.rs` is absent. The Transport card offers USB Serial, an authenticated Wi-Fi listener, and a paired Bluetooth Classic SPP outgoing virtual COM port. Windows may report that port as `Unknown` to `serialport`; Tauri checks Windows device metadata before listing it. See the [Bluetooth pairing and port guide](../Firmware_Templates/BLUETOOTH_TRANSPORT.md). Wi-Fi and Serial require their respective firmware source selection; see the [Wi-Fi guide](../Firmware_Templates/WIFI_TRANSPORT.md).

The Tauri backend owns COM readers and the TCP listener. It validates each complete line as a Rust protocol message and emits it as `espState`; other COM lines are emitted as `espConsole`. `useModuleFront` owns connection state, the registration map and logs; individual Zustand module stores drive controls. The dashboard routes LED and Button registrations, while the LiDAR page is unmounted experimental code. See the [architecture review](../docs/architecture-audit.md). Characterization tests (behavior-recording, not correctness tests) exist for the wire format (`cd protocol; cargo +stable test`) and the desktop log helpers (`cd UI; bun test`); the hardware-free firmware code has host tests (`just test` runs all three suites), and `.github/workflows/ci.yml` runs them on push.
